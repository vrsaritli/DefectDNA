DefectDNA

AI-assisted root-cause analysis (RCA) for closed Azure DevOps defects. DefectDNA imports defects, proposes a root cause for each one with an LLM grounded in your team's previously confirmed RCAs, lets QA Leads approve or correct it, and turns confirmed RCAs into trends that show where defects come from.

React + Vite frontend 4 FastAPI services MongoDB / Atlas Groq LLM (gpt-oss-120b) Cohere embeddings (RAG)

App flow

What a user does, from first sign-in to the dashboard.

  1. Sign in & pick a project.Everyone
    Session cookie login with lockout after repeated failures. Your role on the project (Viewer, QA Lead, Admin) decides what you can do.
  2. Seed the knowledge base (optional, once).Admin
    On Ingestion, upload historical defects that already have a confirmed root cause (Excel or ADO). They become embedded knowledge entries the AI can cite.
  3. Import defects.QA Lead / Admin
    On Import, upload an Excel/CSV export or pull from Azure DevOps (saved query, work item IDs, or closed-by-date). Each upload or pull becomes an import batch.
  4. Analyze.QA Lead / Admin
    On AI analysis, pick an import and click Analyze defects. Duplicates are settled by a rule; the rest are scrubbed, matched to similar confirmed cases and sent to the LLM in batches. Progress shows live.
  5. Review.QA Lead / Admin
    Open a row to see the defect, the AI proposed root cause, the ADO root cause, “Could have been caught by QA?”, confidence, rationale with the sections it was based on, and similar cases. Approve, correct, reject or reopen.
  6. Learn.Automatic
    An approved or corrected RCA is embedded into the knowledge base, so future analyses can cite it, and a trend fact is written for the dashboard.
  7. See trends & export.Everyone
    The Dashboard shows root causes by month, module and SDLC phase from reviewed RCAs only. The defect register and CSV/Excel exports list every defect with its RCA.

Data flow

The browser only talks to the API gateway. Services talk to each other with service tokens and each owns its own MongoDB collections.

Life of one defect

  1. Import — Ingestion parses the row or ADO work item into a defects document (title, description, repro steps, comments, tags, module, release, severity, state, plus the ADO root cause, resolved reason and disposition) and records an import_batches entry.
  2. Queue — The gateway asks ingestion for the batch's closed defects and queues an analyze_defects job in jobs. The AI worker claims it with a lease and checkpoints progress, so a restart resumes where it stopped.
  3. Duplicate rule — If the defect is a duplicate it is stored straight away as DUPLICATE with duplicate_of; no AI call.
  4. Scrub & retrieve — Personal and sensitive values are replaced with placeholders. With RAG on, the defect is embedded and the most similar confirmed cases are retrieved from knowledge_entries.
  5. LLM & validate — Defects are packed into token-budgeted batches; the answer must match a strict JSON schema and the project taxonomy. Invalid answers get one retry, then become NEEDS_MANUAL_RCA. Valid ones are saved to rca_analyses as AI_PROPOSED.
  6. Review — Approve/correct writes the final RCA, embeds it into knowledge_entries and queues a trend fact; the trends worker writes it to trend_facts. Every decision is written to audit_log.

Rules

The behaviour the app enforces, grouped by area.

RCA & display rules

  • The AI picks exactly one root cause, one SDLC phase introduced and one testing gap, only from the project's versioned taxonomy.
  • Other is allowed only when nothing fits, and then the AI must suggest a new category name.
  • Could have been caught by QA? — root cause Code → Y - <testing gap>; any other root cause → N - <root cause>; duplicate → N - Duplicate.
  • Duplicate when Resolved Reason or Disposition says “Duplicate”, or a comment/description says “duplicate of #608”. Root cause shows N/A (duplicate of #608).
  • The ADO root cause is shown next to the AI proposal for comparison and is never sent to the AI.
  • The rationale lists the sections it was based on (title, description, repro steps, comments, tags, similar cases…).
  • Cited similar cases must be among those retrieved for that defect; anything else is rejected.
  • Only closed / resolved / done defects are analyzed. Reviewed RCAs are never overwritten by re-analysis.
  • Only approved and corrected RCAs reach the knowledge base, the dashboard and the trends.

Privacy & AI safety

  • Emails, URLs, secrets/tokens, host names, IPs and long IDs are replaced by [EMAIL], [URL], [SECRET]… before any text leaves the system.
  • Defect text is wrapped in <defect_record> tags and treated as untrusted data: instructions inside it are ignored.
  • Defect text in a job payload is dropped when the job finishes; logs never contain defect text.
  • Each defect is analyzed independently even when batched with others.
  • Any change to the prompt needs a new prompt version and a golden-set run (evals/).

Access & security

  • Viewer: read defects, RCAs and the dashboard. QA Lead: import, analyze, review. Admin: everything, plus knowledge seed, settings, deletion and operations.
  • AI analysis must be enabled per project by an Admin.
  • Sessions expire after 8 hours (30 minutes idle); 5 failed logins lock the account for 15 minutes.
  • State-changing requests need a CSRF token; internal services only accept the gateway's service token.
  • Every review, reopen, import and deletion is written to the audit log.
  • Azure DevOps access is read-only; a pasted query link is never fetched as a URL, only its query ID is used.

Limits (defaults, set in .env)

  • Import file ≤ 10 MiB and ≤ 5,000 rows.
  • ≤ 200 defects per analysis run; ≤ 50 analysis runs per project per day.
  • ≤ 500 LLM calls and ≤ 1,000 embedding calls per project per day.
  • ≤ 8 defects per LLM batch, ~4,500 tokens per request; one retry per failed batch.
  • RAG retrieves the top 5 similar cases with similarity ≥ 0.5.

Tip: “Re-analyze unreviewed” re-runs the AI on an import's defects that are not yet approved or corrected — for example after a prompt change.

Run it locally

  1. Copy .env.example to .env and fill in the MongoDB URI and API keys.
  2. Create the virtualenv and install: python -m pip install -e ".[dev]"; then cd frontend && npm install.
  3. Apply migrations: .\scripts\migrate.ps1; first time only, create the Admin with python -m services.api_gateway.app.bootstrap_admin.
  4. Start everything: .\scripts\start.ps1 and open http://127.0.0.1:5173.
  5. Stop everything: .\scripts\stop.ps1. Logs are in logs\.
